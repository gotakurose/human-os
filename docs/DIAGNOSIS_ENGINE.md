# DIAGNOSIS_ENGINE.md — 診断エンジン設計

## 基本設計思想

診断エンジンは**1つだけ**存在する。新しい診断を追加するたびにエンジンを書き換えるのではなく、エンジンが JSON データを読み込んで動作する。

```
[JSONデータ] → [診断エンジン] → [ユーザースコア + 固定タイプ結果]
```

エンジンは「入力（回答）を受け取り、JSONに定義されたルールに従って、スコアを計算しタイプを決定する」機械として機能する。

### 無料診断が提供する価値の2本柱

無料診断の価値は以下の**両方**で成り立つ。どちらか一方ではない。

| 価値 | 内容 | 実現方法 |
|---|---|---|
| 自分のスコアが可視化される | 5軸のレーダーチャートで「自分の強みと弱み」が一目でわかる | ユーザーの実スコアで描画 |
| 固定タイプで共有できる | MBTIのように「同じタイプだった！」と比較・共有できる | 固定タイプ・キャラクター・コメントを表示 |

スコアはユーザー固有、タイプ結果は固定。この**ハイブリッド構造**が本プラットフォームの核心。

## 固定タイプ制の考え方

### なぜ固定タイプ制か

AI診断サービスの多くは「あなただけの個別結果」を生成するが、このプラットフォームは逆の思想を採用する。

- **MBTIモデルの参考**：MBTIは16タイプのいずれかに分類される仕組み。「自分はINFJだった」と伝えることで、他者との共感や比較が生まれる。本プラットフォームもこの「タイプ共有体験」を核に設計する
- **共有可能性**：「私も同じタイプだった！」という体験が口コミ・SNS拡散を生む
- **一貫性**：同じ回答なら何度やっても同じ結果。信頼性の担保
- **コスト効率**：結果を毎回AI生成しないため、大量アクセス時もコストが増加しない

### 固定タイプの構成要素

各タイプは以下の要素を持つ（すべてJSONに事前定義）。`famousExamples` は使用しない。

```json
{
  "id": "sales-monster",
  "name": "営業モンスター",
  "character": {
    "name": "突破口のケンジ",
    "imageUrl": "/images/characters/sales-monster.png",
    "color": "#FF6B35"
  },
  "representativeScores": {
    "logic": 60,
    "execution": 85,
    "sales": 95,
    "creativity": 55,
    "management": 50
  },
  "summary": "人を動かすことに圧倒的な才能を持つ、生まれながらの交渉人。",
  "detail": "あなたは...",
  "strengths": ["人を巻き込む力が抜群", "数字にコミットできる", "逆境でも前進できる"],
  "weaknesses": ["細かいプロセス管理が苦手なことがある", "一人で抱え込みすぎることがある"],
  "compatibleTypes": ["strategist", "creator"],
  "recommendedRoles": ["営業リーダー", "事業開発", "プロダクトマネージャー"],
  "idealEnvironments": ["成果主義の組織", "裁量が大きいポジション", "外部との接点が多い業務"],
  "growthTips": ["論理的な提案書の作成を練習する", "チームへの権限委譲を意識する"],
  "sarcasticComments": [
    "話の長さより、中身を磨け。",
    "熱意は武器だが、相手の話も聞いてあげて。"
  ],
  "affiliateLinks": [
    { "label": "営業力強化におすすめの一冊", "url": "..." }
  ]
}
```

**`famousExamples` を使わない理由：** 有名人が実際に診断を受けたわけではなく、誤認・権利・印象リスクがある。代わりに `recommendedRoles`・`idealEnvironments`・`growthTips` でタイプの活用イメージを伝える。

## スコアリング方式（`engineType: "radar"`）

### 概要

複数の軸を数値化し、スコア分布でタイプを決定する方式。社会人能力値診断に使用。

### 5軸の定義（社会人能力値診断）

| axisId | 表示名 | 測定する特性 |
|---|---|---|
| `logic` | 論理力 | 論理的思考・課題の構造化・根拠に基づく判断 |
| `execution` | 実行力 | 行動の速さ・やりきる力・タスク管理 |
| `sales` | 営業力 | 伝える力・人を動かす力・対外的な交渉力 |
| `creativity` | 創造力 | アイデア発想・新しい視点・課題の再定義 |
| `management` | 管理力 | チーム・プロセス・品質・リスクの管理 |

### 質問JSONの構造

```json
{
  "id": "q01",
  "text": "締め切りが近いとき、あなたはどう行動しますか？",
  "options": [
    {
      "text": "優先順位を決めて即座に取りかかる",
      "scores": { "execution": 3, "logic": 1 }
    },
    {
      "text": "チームに相談してタスクを分担する",
      "scores": { "management": 3, "sales": 1 }
    },
    {
      "text": "全体を見渡して計画を立て直す",
      "scores": { "logic": 3, "management": 1 }
    },
    {
      "text": "自分なりの突破口を見つける",
      "scores": { "creativity": 2, "execution": 2 }
    }
  ]
}
```

スコアに使う軸は `logic` / `execution` / `sales` / `creativity` / `management` の5つのみ。

### スコアリングロジック

1. 全質問の回答を集計し、軸ごとのスコアを合計する
2. 合計スコアを最大値で割り、0〜100 にノーマライズする
3. ノーマライズ済みスコアを `scoring.json` のルールと照合してタイプを決定する

### タイプ判定ロジック（scoring.json）

```json
{
  "method": "dominant-axis",
  "rules": [
    {
      "typeId": "sales-monster",
      "condition": {
        "dominant": ["sales", "execution"],
        "minScore": { "sales": 70 }
      }
    },
    {
      "typeId": "strategist",
      "condition": {
        "dominant": ["logic", "management"],
        "minScore": { "logic": 70 }
      }
    },
    {
      "typeId": "creator",
      "condition": {
        "dominant": ["creativity"],
        "minScore": { "creativity": 72 }
      }
    }
  ],
  "fallback": "all-rounder"
}
```

- `dominant-axis`：最もスコアが高い軸の組み合わせでタイプを決定
- `fallback`：どの条件にも合致しない場合のデフォルトタイプ

## レーダーチャート表示

### 表示方針

個人結果画面では**ユーザー自身のノーマライズ済みスコア**をレーダーチャートで描画する。

- 軸ラベル・軸の順序・最大値・カラーは `meta.json` に定義
- 描画するのはユーザーの実スコア（タイプの代表スコアではない）
- タイプの `representativeScores` は参照情報として types.json に保持するが、個人結果ページには表示しない

**この方針の理由：** 自分のスコアが可視化されることで「なぜこのタイプになったか」が直感的に伝わる。単なるタイプ表示より、自己理解の解像度が上がる。

### 表示例

```
個人結果画面のレーダーチャート：
  論理力   72（このユーザーの実スコア）
  実行力   85
  営業力   91  ← 最高値 → "営業モンスター" に判定
  創造力   48
  管理力   53
```

## 結果ページの2層構造

結果体験は目的の異なる2つのページで構成する。

### A. 個人結果画面

| 項目 | 内容 |
|---|---|
| URL例 | `/diagnoses/business-skills/result` |
| 目的 | 診断完了直後のユーザー体験 |
| 表示内容 | ユーザーの実スコアによるレーダーチャート + タイプ名 + キャラクター + 固定コメント |
| SEO | 対象外（クライアントサイドで回答スコアを受け取り表示） |
| シェア | タイプ別固定ページへの誘導リンクを表示 |

診断完了後、クライアントサイドで計算したスコアをもとにタイプを決定し、このページに遷移する。URLにスコアは含まれない。

### B. タイプ別固定ページ

| 項目 | 内容 |
|---|---|
| URL例 | `/diagnoses/business-skills/results/sales-monster` |
| 目的 | SNSシェア・SEO・「同じタイプだった」共有体験 |
| 表示内容 | タイプ説明・キャラクター・代表能力値・強み弱み・おすすめリンク |
| SEO | 対象（タイプ名がURL・タイトルに入る） |
| OGP | タイプ別固定OGP（`opengraph-image.tsx` で生成） |
| SSG | ビルド時に全タイプ × 全診断分を事前生成 |

MBTIの「INFJ 解説ページ」に相当するページ。ユーザーはここのURLを友人に共有することで「同じタイプだった」体験が生まれる。

## 16タイプ診断方式（`engineType: "type16"`）

### 概要

4つの独自軸それぞれで2択を積み重ね、最終的に16通りのオリジナルタイプに分類する方式。

### MBTIとの関係について

MBTIは参考モデルとして位置づける。実装上は**MBTIの軸・コード・タイプ名をコピーしない**。

- EI / SN / TF / JP という軸体系は使わない
- ENTJ / INFP などのコードは使わない
- タイプ名もオリジナルの日本語名称を使う

理由：MBTI は商標管理が厳格であり、コピーは権利上のリスクがある。また、オリジナル軸で設計することでプラットフォームとしての独自性が生まれる。

### オリジナル軸の設計例（診断ごとに独自定義）

```json
{
  "axes": [
    {
      "id": "axis1",
      "label": "行動スタイル",
      "poles": [{ "id": "A", "label": "先手型" }, { "id": "B", "label": "観察型" }]
    },
    {
      "id": "axis2",
      "label": "思考スタイル",
      "poles": [{ "id": "A", "label": "論理重視" }, { "id": "B", "label": "直感重視" }]
    },
    {
      "id": "axis3",
      "label": "関係スタイル",
      "poles": [{ "id": "A", "label": "協調型" }, { "id": "B", "label": "独立型" }]
    },
    {
      "id": "axis4",
      "label": "計画スタイル",
      "poles": [{ "id": "A", "label": "構造型" }, { "id": "B", "label": "柔軟型" }]
    }
  ]
}
```

### タイプ決定

- 各軸でどちらの回答が多かったかをカウント
- 4軸の組み合わせでオリジナルのタイプコードを生成（例：`AABA`, `BBAB`）
- そのコードに対応するタイプ定義を `types.json` から取得
- タイプ名はコードではなくオリジナルの名称で表示（例：「先読みの設計者」「直感の開拓者」）

## 条件分岐型診断方式（`engineType: "branch"`）

### 概要

フローチャートのように、回答によって次の質問が変わる方式。「家買いたい？現在地チェッカー」などに使用。

### 質問JSONの構造

```json
{
  "id": "q01",
  "text": "今の住まいの状況は？",
  "options": [
    { "text": "賃貸に住んでいる", "next": "q02a" },
    { "text": "実家にいる", "next": "q02b" },
    { "text": "すでに持ち家がある", "next": "result-owner" }
  ]
}
```

- `next` に次の質問ID or 結果IDを指定
- 結果IDが指定された場合は即座に結果表示
- 質問数は分岐によって変わる（3問で終わる人もいれば10問の人も）

## コメント表示方式

### コメントの4層構造

すべてのコメントは事前に JSON に定義し、無料診断では AI 生成は使わない。

```
① タイプ固定コメント（全員に表示）
     └── タイプ説明（summary / detail）
     └── 強み（strengths）
     └── 弱み（weaknesses）
     └── おすすめ職種・環境・成長アドバイス

② 軸別スコアコメント（スコアに応じて追加表示）
     └── 上位軸：「あなたの営業力スコアは特に高い水準です」
     └── 下位軸：「管理力を意識的に高めることで、さらに活躍の幅が広がります」

③ 辛辣コメント（タイプごとの固定候補からランダム表示）
     └── `sarcasticComments` 配列からランダム選択
     └── ユーモアのある「刺さる一言」でシェア欲求を高める
     └── AIは使わない（事前に5〜10本を定義しておく）

④ 有料版AI個別コメント（将来・課金後のみ）
     └── ユーザーの回答データを AI に渡して個別分析
     └── 「あなたのこの回答傾向は…」という個人に響くフィードバック
```

### コメント選択ロジック

```
1. タイプIDから types.json のタイプ定義を取得
2. ① タイプ固定コメントをそのまま表示
3. ② ユーザースコアを参照し、上位軸・下位軸の軸別コメントを追加表示
4. ③ sarcasticComments からランダムで1件選んで表示
5. （有料版のみ）④ AIにユーザー回答データを渡して個別コメントを生成
```

## AIを使う範囲と使わない範囲

### AIを使わない範囲（無料体験の核心）

| 処理 | 方法 |
|---|---|
| スコアリング | JSON定義 + 純粋な計算処理 |
| タイプ判定 | JSON定義のルールに基づく条件判定 |
| レーダーチャート描画 | ユーザーの実スコアで描画 |
| タイプ固定コメント表示 | JSON定義の固定テキスト |
| 軸別スコアコメント | JSON定義 + スコア閾値による条件分岐 |
| 辛辣コメント | JSON定義の候補からランダム選択 |
| キャラクター表示 | 固定画像のマッピング |
| OGP画像生成 | @vercel/og でタイプ別固定OGPを生成 |

### AIを使う範囲（設計・有料機能）

| 用途 | タイミング |
|---|---|
| 診断の質問・タイプ設計支援 | 新診断作成時（開発者向け） |
| タイプ別コメント・辛辣コメント候補の下書き | 診断コンテンツ制作時 |
| 有料個別レポート生成 | Phase 4以降、ユーザーが購入した場合のみ |
| 複数診断の統合分析（Human Profile） | Phase 4以降 |
| BtoBチーム分析レポート | BtoB展開時 |

### この設計の利点

- 無料診断は**リクエストごとのAIコストがゼロ**。大量アクセスに耐えられる
- ユーザーは**自分のスコアで自己理解**し、**固定タイプで他者と比較・共有**できる
- 診断結果に**一貫性・再現性**があり、ユーザーが信頼できる
- 有料AIレポートの**価値が明確**（無料では得られない個別パーソナライズ）
- 将来のAI活用範囲を**プラグイン的に追加**できる設計
